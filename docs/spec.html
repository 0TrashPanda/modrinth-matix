1. Overview

Modlist Matrix shows which Minecraft versions a set of mods supports on a given loader. It helps you pick the newest version most of your mods run on, then get the client and server files for that version.

Version 1 is a single static page. The list lives in a textarea, which you currently keep in a file on pCloud. The rewrite adds accounts and saved lists. Its main goal is that the list is stored in the app.

Goals

  • Saved lists tied to an account, so text files are no longer needed.
  • Lists that can be private, shared with friends, or public.
  • Everything v1 does, but faster and with less manual URL editing.
  • Low load on the home-lab server. The browser keeps doing the heavy API and download work.

Audience

You and your friends. The site can be reached publicly, but registration needs an invite. The expected user count is small (under ~50), so this spec doesn't plan for scaling.

Non-goals

  • A launcher. The app never installs mods into a Minecraft instance.
  • Hosting or mirroring mod files.
  • Open sign-up, or any monetisation.

3. Accounts and invites

Sign-in

  • Sign-in uses Google only (OAuth 2.0 / OpenID Connect). The app stores no passwords.
  • Sessions use secure, HTTP-only cookies and last 30 days, renewed on activity.
  • The architecture allows adding other providers later, such as Discord or GitHub, without changing the data model.

Invite-only registration

  • The first Google account to sign in becomes admin, or the admin is set in server config.
  • Anyone else signing in with Google gets an account only if they present a valid invite. Without one they see "You need an invite" and no account is created.
  • An invite is a link like /invite/<code>. Opening it and signing in creates the account.
  • Invite options: single-use or N uses, an optional expiry date, and an optional lock to one email address.
  • The admin can create and revoke invites and see who used each one.
  • Optional setting: normal users can create a limited number of invites (default 0).

Roles

RoleCan
AnonymousView public lists. Use the matrix with a temporary, unsaved list, the same as v1.
UserEverything above. Create, edit and delete their own lists. Share lists and fork lists.
AdminEverything above. Manage invites, disable or delete users, and change instance settings.

Profile

  • Display name and avatar come from Google and can be edited.
  • A unique handle is used in share dialogs and public URLs, for example /u/jonah/my-pack.
  • "Delete my account" removes the user's lists. Shares with other users are revoked.

4. Modlists and visibility

A modlist has

  • A name, an optional description, and an optional icon chosen from a mod in the list.
  • Default settings: loader, target Minecraft version (optional), whether to include snapshots, and the client or server focus.
  • Ordered entries. Each entry is an OR-group of one or more alternatives (see §11).
  • Optional sections inside the list, such as "Performance" or "QoL", to group entries.
  • Tags or folders for organising lists on the dashboard.

Visibility

LevelWho can seeWho can edit
PrivateOwner onlyOwner
SharedOwner, plus specific users invited by handleOwner, plus users given the editor role
PublicAnyone with the link, including anonymous visitors. Public lists also appear on the owner's profile page.Owner, plus editors
  • Shared and public both support per-user viewer and editor roles. Public only adds anonymous read access.
  • Any signed-in user who can view a list can fork it into a private copy. The copy records where it came from.
  • Lists you've been given access to appear on your dashboard under "Shared with me".

History

  • Every save creates a revision. You can view, diff and restore old revisions.
  • Revisions record who made the change, which matters when editors are involved.
  • Undo and redo work inside the editor before saving.
  • If two editors save at the same time, the second save is rejected with "List changed, reload". Merging is not required.

Import and export of lists

  • Import plain text in the v1 format, so the existing pCloud files load directly. This is required for phase 1.
  • Export to the same plain-text format, for backups.
  • Import and export JSON (full fidelity, including notes, pins and sections).
  • Import a Modrinth .mrpack by reading its file hashes and matching them to projects.

5. List editor

  • P1Paste URLs in the v1 format, which is parsed into entries. This is the quick path for power users.
  • P2In-app search of Modrinth (and later CurseForge) projects, showing icon, downloads, loaders and last update. Add a result as a new entry or as an alternative to an existing entry.
  • P2Visual side controls replace the [!c] syntax: per alternative, choose "Auto (Modrinth)", "Fallback: client/server/both" or "Force: client/server/both". The text format stays for import and export.
  • P2Drag and drop to reorder entries, move entries between sections, and merge two entries into one OR-group or split them apart.
  • P2Per-entry notes (free text) and a required/optional flag. Optional entries are left out of the best-version calculation by default.
  • P3Version pin: lock an alternative to a specific mod version, so update checks skip it.
  • P3Project types: mods, resource packs, shaders and datapacks. Entries show their type, and the type affects which loader filter applies (shaders filter by Iris or OptiFine, resource packs ignore the loader).
  • P2Duplicate detection: warn when the same project appears twice.
  • P2Validation: flag URLs that don't resolve, deleted or archived projects, and projects that don't support the list's loader at all.

6. Compatibility matrix

  • P1Parity with v1: rows as entries, columns as versions sorted newest first, cells split per alternative and coloured by side, header counts and highlight, and row toggling.
  • P1Sticky header row and first column, so a large matrix stays readable.
  • P1Loading progress ("Fetched 23 / 41 projects") and visible per-row errors instead of silent console logs.
  • P2Target version view: select a version to see which entries block it. For each blocker it shows the newest version that entry does support, and whether an alternative would fix it.
  • P2Column filters: hide versions with zero support, set a version range (for example 1.20 to newest), and collapse patch versions into their minor version.
  • P2Release channel: choose to count only release, or also beta and alpha mod versions. Cells show when support exists only through beta or alpha versions.
  • P2Row sort and filter: by name, by side, or by support for the target version, plus a text filter.
  • P3Loader comparison: show counts for several loaders side by side, to answer questions like "would NeoForge get me a newer version?"
  • P3Staleness: mark entries whose project hasn't been updated in more than N months.
  • P3Dependency and conflict view for a chosen version: show required dependencies that aren't in the list, and Modrinth incompatible dependencies between entries.
  • P1Cell details: hovering or tapping a cell shows the mod version that would be used, its release channel and its date.
  • P2Mobile layout: on narrow screens, show a "per version" list view instead of the full grid.

Side resolution (unchanged rules, improved input)

For each alternative, the side is resolved in this order:

  1. A forced override ([!x]) wins.
  2. Otherwise, Modrinth's client_side and server_side values are used.
  3. If Modrinth's answer is unknown, the fallback override ([x]) is used.

Change from v1: v1 only looks at required. The rewrite also treats optional as "works on that side". For example, a mod that is client_side: optional and server_side: required counts as both, while client_side: required and server_side: unsupported counts as client. The exact mapping should be shown in the UI.

7. Downloads and export

Approach: all mod files go from the platform's CDN straight to the user's browser. The server never relays jar files.

This fits your low-upload home lab. Modrinth's CDN allows cross-origin requests, so the browser can fetch the jars itself and build a zip locally (for example with a zip library such as fflate). The server only ever sends small JSON.

  • P1Open download tabs, as in v1: client or server pack, choice of alternatives, and dependencies.
  • P2Download as zip: the browser fetches every selected jar and builds client.zip, server.zip, or one zip with client/ and server/ folders. It shows progress and checks each file's SHA-1/SHA-512 from the API.
  • P2Review before download: a table of every file that will be downloaded, including resolved dependencies and the alternative chosen. Files can be unticked.
  • P2Recursive dependencies: required dependencies of dependencies are included too. v1 only goes one level deep.
  • P2Remember choices: the alternative picked for each entry, per version and pack side, is saved with the list so the modal is pre-filled next time.
  • P3Export .mrpack: a Modrinth modpack file that the Modrinth App, Prism and others can import. It contains only URLs and hashes, so it's tiny and needs no file downloads.
  • P3Export a download script (PowerShell and bash) that fetches the files and checks their hashes. Useful for setting up a server directly on the home lab.
  • P3Update check for a saved list and its chosen version: "4 mods have newer versions for 1.21.4 Fabric", with a changelog link for each.

8. Platforms

Modrinth P1

  • Called directly from the browser. No key is needed, and the limit is about 300 requests per minute per IP. Because the requests come from each user's own IP, the server is never rate limited.
  • Use batch endpoints where possible to cut request counts: GET /v2/projects?ids=[…] for project metadata in one call, and POST /v2/version_files for hash lookups.
  • Version lists still need one call per project: GET /v2/project/{id}/version.
  • Saved entries store the project ID as well as the slug, so renamed slugs don't break lists.

CurseForge P3

Why CurseForge is harder: its API needs an API key from the CurseForge console, and the terms say the key must not be shown to users. So the browser can't call CurseForge directly with the key, unlike Modrinth.

Proposed approach: the server runs a thin, cached proxy for CurseForge metadata only (projects, file lists, dependencies). This is small JSON, so upload speed isn't a concern. The server caches responses (for example 1 hour for files and 24 hours for project info), which keeps it well under CurseForge's limits for a few users.

Downloads: the browser fetches files straight from CurseForge's CDN if cross-origin requests are allowed. Otherwise those files fall back to "open in tab". Some CurseForge authors disable third-party downloads; those entries always fall back to a link to the CurseForge page.

  • An alternative can be a Modrinth or CurseForge project, so one OR-group can mix platforms.
  • Loader and version naming differ between the platforms and must be normalised to one internal format.
  • CurseForge's side information is weaker than Modrinth's. CurseForge entries default to "unknown" side, so the overrides matter more.
  • If no API key is configured, the instance hides CurseForge features.

9. Quality of life

  • P1Client-side cache of API responses in IndexedDB, with a TTL (for example 1 hour for versions and 24 hours for project info), so reopening a list is nearly instant. A "Refresh" button bypasses the cache.
  • P1Autosave of drafts locally, so a closed tab doesn't lose unsaved edits.
  • P1Dark and light themes, defaulting to the system setting.
  • P2Keyboard shortcuts: / to search, Ctrl+S to save, Ctrl+Z to undo, and arrow keys to move around the matrix.
  • P2Dashboard: your lists, "Shared with me", recently opened lists, and quick stats per list (entry count and best version).
  • P2Shareable matrix state: the URL keeps the loader, target version and filters, so a link opens the same view.
  • P3Import from a mods folder: drop jar files on the page. The browser hashes them locally and matches them through POST /v2/version_files. Files never leave the browser.
  • P3List comparison: diff two lists, or two revisions of one list.
  • P4Activity notifications, such as "a friend edited a shared list".

10. Architecture constraints

These constraints come from the home lab setup and will guide the stack choice.

ConstraintConsequence
The server has low upload bandwidthThe server stores and serves only small JSON and the app bundle. The app bundle should be small and cacheable, ideally behind a CDN or tunnel cache. No file proxying.
The server must not be rate limited by platformsModrinth calls stay in the browser. Only CurseForge goes through the server, and it is cached.
A handful of usersA single process and a single database file (for example SQLite) are fine. No queue, no cluster.
The server is publicly reachableHTTPS (via reverse proxy or tunnel), invite-only sign-up, CSRF protection, rate limits on auth and invite endpoints, and strict authorisation checks on every list endpoint.
Home lab opsShips as one Docker image (or a compose file). Config comes from environment variables. Backups mean copying the database file, documented in the README.

Responsibilities

  • Browser: all Modrinth requests, the matrix calculation, the API cache, zip building and jar hashing.
  • Server: Google OAuth, sessions, invites, list storage and permissions, revisions, and the CurseForge proxy.

11. Data model (logical)

User          id, google_sub, email, handle, display_name, avatar_url,
              role (user|admin), created_at, disabled_at

Invite        id, code, created_by → User, max_uses, uses,
              expires_at, locked_email, revoked_at

InviteUse     invite → Invite, user → User, used_at

Modlist       id, owner → User, name, slug, description, icon,
              visibility (private|shared|public),
              loader, target_mc_version, include_snapshots,
              release_channels, forked_from → Modlist,
              current_revision, created_at, updated_at

ModlistShare  modlist → Modlist, user → User, role (viewer|editor)

Revision      id, modlist → Modlist, author → User, created_at,
              content (JSON snapshot of sections + entries)

-- inside Revision.content --
Section       id, name, order
Entry         id, section_id, order, enabled, required, note,
              alternatives[]
Alternative   platform (modrinth|curseforge), project_id, slug,
              cached_title, cached_icon, project_type,
              side_mode (auto|fallback|force), side (client|server|both),
              pinned_version_id, note
DownloadPick  mc_version, pack_side (client|server), entry_id → alternative index

Storing list content as a JSON snapshot per revision keeps history simple and matches how lists are edited (as a whole). Lists are small, so storage size is not a concern.

13. Known issues in v1 (fix in the rewrite)

  • Mod links are always built as /mod/<slug>, which is wrong for plugins, resource packs and other types.
  • optional sides are treated as unknown (see §6).
  • Dependencies are resolved only one level deep, and they aren't filtered by pack side.
  • When a dependency is a project ID, the fetched version may be a beta even if a release exists. Releases should be preferred.
  • Failed fetches are only logged to the console, so the row silently goes empty.
  • Every run re-fetches every project, and the project and version endpoints are called separately per alternative.
  • Opening many tabs at once is often blocked by the browser's pop-up blocker.
  • Loader and snapshot settings aren't remembered between visits.

14. Open questions

  • Domain and tunnel. Answered: nginx reverse proxy on the home lab. nginx serves the app's static files compressed (brotli or gzip) with long-lived cache headers, so each browser downloads the bundle once.
  • Should public lists be listed or searchable on an "Explore" page, or reachable only by link?
  • Should anonymous visitors be able to use the matrix with an unsaved list, as v1 allows today? This spec assumes yes.
  • Is a CurseForge API key already available, or does one need to be requested?
